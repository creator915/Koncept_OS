# v10 设计文档：图升级为 source of truth

> 起源：2026-05-13 v9.4 batch（5 实例 Terraria）暴露 evidence-stale cascade、frag 体积失控、implSymbol 桥在 Python 失效——三条都指向同一个底层错配：path-addressed verification + mutable single-file deliverable + per-object atomic invariant 三者无法共存。
> 配套报告：[KonceptOS_kcpos_report_2026-05-13.md](../../../KonceptOS_kcpos_report_2026-05-13.md)

## 1. 目标

把 graph 从"路径索引层"升级为 **source of truth**：

- 每个 object 的实现代码（fragment）**直接存在 graph 节点上**（`obj.impl_content`），不再通过文件路径间接引用
- 文件（`K/frags/X.js`、`index.html`）退化为**graph 的投影**——可重新生成、可丢弃、不参与 verification
- evidence 改成内容寻址（`(object_id, content_hash) → bundle`），消灭 stale 概念

## 2. 为什么这样改

| 现状 | 改后 | 收益 |
|---|---|---|
| `obj.impl="index.html"`（共享）+ `obj.implFragment="K/frags/X.js"`（独立） | `obj.impl_content="function X(){...}"` 一字段搞定 | 删 1 个字段 |
| session_build 改写文件 → bundle hash 过期 → cascade | session_build 是纯投影，不参与 evidence | 删 evidence-stale / spec-stale / runtime-trace-stale 三条规则 |
| SymbolHash 抽取单文件 HTML 里的函数体 | impl_content 本身就是函数体，hash 直接算 | 删 SymbolHash / ExtractSymbolFragment / SymbolFragmentHash 三个 API |
| ImplSymbol 桥接 object 名跟函数名 | object_id 跟随目标语言惯例，无桥接需求 | 删 ImplSymbol 字段 + 相关 harness 双绑定逻辑 |
| 文件存在性、文件 hash 进 19 条 gate 规则 | 文件不参与 verification | 删 5+ 条文件存在/staleness 规则 |
| agent 通过 write_file 改交付物 → 链条无法干预 | agent 只能通过 graph_merge_object 改 impl_content → 物理上不可绕过链 | 杜绝 v94-04 那种"agent 跟链对抗"的失败模式 |

**净化效果**：3 个抽象（SymbolHash / implFragment / implSymbol） + 5+ 条 gate 规则可以删除。模型显著简化。

## 3. Schema 变更

### 3.1 Object 节点

```diff
 type Object struct {
     ID              string
     Def             string              // K/defs/X.{py,js,go,...} — 签名文件
-    Impl            *string             // 交付文件路径（共享或独立）
-    ImplSymbol      string              // object_id 跟函数名不一致时的桥
-    ImplFragment    string              // HTML 分支下的真实代码片段路径
+    ImplContent     string              // ★ 真实代码内容，直接持有
+    ImplLang        core.Lang           // ★ 从 ImplContent 探测的语言
     Consumes        []string
     Produces        []string
     Mutates         []string
     PortObservation map[string]string
     Intent          string
+    StoryPoints     int                 // ★ v9.5 — 1/2/3/5/8/13
+    StoryRationale  string              // ★ v9.5 — 为什么是这个分
     Status          Status              // declared / implementing / confirmed
     StatusSession   *string
 }
```

兼容性：v10 的 Graph 读取器接受旧 schema（Impl/ImplFragment 字段），把它们 lazy-migrate 进 ImplContent。

### 3.2 Bundle（evidence 档案）

```diff
 type Bundle struct {
     ObjectID     string
-    SourceHash   string                 // 文件级 hash
-    SymbolHash   string                 // v9.0.2 引入的 per-function hash
+    ContentHash string                  // ★ ImplContent 的 SHA-256，唯一锚点
     Compile     *CompileSection
     Test        *TestSection
     Spec        *SpecSection
     RuntimeSmoke *RuntimeSmokeSection
     Accepted    *AcceptedSection
     UpdatedAt   time.Time
 }
```

bundle 文件名仍是 `.kcpos/typecalc/<object_id>.json`（per-object 一份）；但**bundle 是否有效的唯一判据是 `bundle.ContentHash == hash(current obj.ImplContent)`**——不一致即 stale，等价于"不存在"。

### 3.3 Project-level deliverable

```diff
+type ProjectDeliverable struct {
+    Path     string                     // 例: "index.html"
+    Kind     string                     // "html" / "python_module" / "go_binary" / ...
+    Renderer string                     // 用哪个 projector
+}
```

deliverable 在 graph 顶层声明一次（不是 per-object）。session_build 拿到这个声明 + 全部 object 的 ImplContent，渲染出文件。这条数据不参与 verification。

## 4. Tool API 变更

### 4.1 graph_merge_object 新规约

```
graph_merge_object id=<id> patch={
    impl_content: "function X(a, b) { ... }",   ← 新字段
    impl_lang: "javascript",                    ← 新字段（可选，从 content 自动探测）
    story_points: 3,                            ← v9.5 必填
    story_rationale: "单循环遍历前缀",            ← v9.5 必填（≥ 10 字符）
    ...
}
```

**约束**：
- `impl_content` 不能为空（设了就有内容）
- `impl_content` **必须只含一个顶层函数声明**（规则见 §6）—— 违反则拒绝
- `story_points` 仅接受 1/2/3/5/8/13 —— 其他值拒绝
- `story_points >= 8` 时，**禁止把 status 转到 implementing**——必须先 `graph_split_object` 拆分

### 4.2 新工具：graph_split_object

```
graph_split_object id=<id> rationale="..."
  → LLM 子 call 生成 sub-objects 提议
  → 返回 {sub_objects: [{id, intent, story_points, ...}]}
  → agent 决定接受/编辑后调用 graph_create_object 各 sub-object，再 graph_delete_object 原 id
```

### 4.3 废弃工具/字段

| 现有 | 状态 |
|---|---|
| `write_file path=K/frags/*` | **废弃**——拒绝写 frag 路径，提示用 graph_merge_object impl_content |
| `write_file path=index.html` | **废弃**——拒绝写 deliverable 路径，提示用 session_build |
| `graph_merge_object patch.impl=...` | v10 接受但 lazy migrate 进 impl_content；新代码不应用 |
| `graph_merge_object patch.implFragment=...` | 同上 |
| `graph_merge_object patch.implSymbol=...` | **拒绝**——object_id 跟随目标语言惯例 |
| `typecalc_compile path=...` | 改成 `typecalc_compile id=<object_id>`——从 graph 读 impl_content |

write_file 仍可用于：
- 写 SPEC.md / README.md / docs/*.md（人类阅读用，不进 chain）
- 写 K/defs/*.{py,js,go}（签名文件，参考但不验证）
- 写 K/checkpoint.json（项目级 must 清单）

不能用于：任何参与 verification 的代码内容。

## 5. Chain 变更

### 5.1 主链路

```
                            ┌── compile（读 graph）
                            ├── describe（读 graph）
confirm_object id=X  ──→    ├── synthesize_tests（读 graph）
                            ├── test（写 ImplContent + TestCode 进临时文件、跑、删）
                            ├── review（读 graph + bundle）
                            └── MarkConfirmed
```

**关键改动**：每一步都从 `graph.Objects[id].ImplContent` 读源，**不读文件**。文件层不参与 verification 流程。

### 5.2 HTML 分支

```
confirm_object id=X  ──→  compile → describe → review → MarkConfirmed
                                                ↑
                                          仅读 ImplContent

project_smoke              ←── 独立的项目级 gate（不是 per-object）
  ├── session_build         （graph → index.html，pure projection）
  └── runtime_smoke         （Playwright 跑 index.html）
```

**关键改动**：
- runtime_smoke 不再 per-object 跑——它是项目级闸门
- 每个 object 的 confirm 只需要 compile + describe + review（HTML 分支跟普通分支统一）
- session_build 从 confirm_object 的链里**摘出来**，变成 root 完成前的项目级步骤之一

这条改动让 evidence-stale cascade **从根上消失**：因为 session_build 不再在 per-object 链路上跑，它不再有机会反复改写共享文件。

### 5.3 删除的规则

| 规则 | 原因 |
|---|---|
| `evidence-stale` | ContentHash 比对取代，逻辑融入"bundle 是否有效"的判定 |
| `spec-stale` | 同上 |
| `runtime-trace-stale` | runtime_smoke 退出 per-object 链路 |
| `runtime-trace-missing` (HTML 分支) | 同上 |
| `port-observation-required` (HTML 分支) | impl_content 直接可解析，端口校验回归普通规则 |
| `value-space-empty` (HTML 分支) | 同上 |
| `runtime-smoke-required` | 改成 project_smoke 的闸门，不再 per-object |

## 6. ImplContent 内容形态约束

```
v10 接受的 impl_content 必须是「单顶层函数声明」：

合法：
  function GameMain(world, player) { ... }                  ← JS
  const GameMain = (world, player) => { ... }               ← JS arrow
  def has_close_elements(numbers, threshold):               ← Python
  func GameMain(world *World) error { ... }                 ← Go

非法（拒绝）：
  function A() {} function B() {}                          ← 多个顶层函数
  function A() {}; var x = 1;                              ← 顶层有非函数语句
  // (空 / 仅注释)                                          ← 没函数
```

这条规则用语言级 AST 解析判定（Python 用 ast 模块、Go 用 go/parser、JS 用一个简单 lexer）。**实施在 graph_merge_object 的校验层，agent 写入即被检查**。

效果：让"超大对象"在 schema 层不可表达——agent 想塞多个函数到一个 object，必须 split。

## 7. 文件层的位置

```
ProjectDir/
├── SPEC.md                 ← agent 写、人读
├── K/
│   ├── graph.json          ← v10 的 source of truth，含全部 ImplContent
│   ├── defs/X.{py,js,go}   ← 签名文件（参考用，不验证）
│   └── checkpoint.json     ← 项目级 must 清单
├── .kcpos/typecalc/X.json  ← evidence bundle（per-object）
└── (build outputs)          ← session_build 投影生成、可重建、不进版本控制
    ├── code.py / code.go / ...
    └── index.html / K/frags/X.js
```

`(build outputs)` 段是关键：v10 下，这些是**自动生成的投影**，不进 graph、不进 chain。session_build 是它们的唯一作者。删了重建一份就能玩。

## 8. 迁移路径

### 8.1 向后兼容

v10 的 Graph 加载器：
1. 读 graph.json
2. 对每个 object：
   - 若有 `impl_content` 字段 → 用 v10 模式
   - 若只有 `impl` + `implFragment` → 读 `K/frags/<id>.js`（或 `<impl>`）的内容，填入 `impl_content`，**只读这一次**
   - 持久化时只写 v10 schema

旧 fixture（v94 batch、assembly-test）按这个路径自动迁移。

### 8.2 现有 evidence

bundle 文件保留，但 v10 加载时按 ContentHash 重新核对：
- bundle.SourceHash 等于 hash(ImplContent) → 接受为有效证据
- 不等 → 视为 stale，等价于"无证据"，gate 拒绝放行

agent 重跑 confirm_object 后会生成新 bundle（带 ContentHash）。

### 8.3 阶段切换

阶段 1（v10 schema 兼容期）：
- 加 Object.ImplContent / Bundle.ContentHash 字段
- 加载器做向后兼容
- chain 同时支持读文件和读 graph（优先 graph）

阶段 2（v10 默认期）：
- graph_merge_object 默认产生 impl_content
- write_file K/frags/* 弃用警告
- 旧 fixture 仍能跑

阶段 3（v10 强制期）：
- write_file K/frags/* / index.html 拒绝
- 旧 fixture 强制迁移

## 10. 决策点 / 待商

| # | 议题 | 当前方案 |
|---|---|---|
| 1 | impl_content 是否做 deduplication（同样的 content 多个 object 共用）| 不做。v10 强制单顶层函数 + per-object 隔离，dedup 无必要 |

## 附录 A：v9.4 vs v10 数据流对比

### v9.4（current）

```
agent → write_file(K/frags/X.js)
         → 文件系统
         → typecalc_compile（读文件） → bundle.SourceHash
         → session_build（重写 index.html）  ← 改 hash
         → review（比对 bundle.SourceHash vs current file hash）→ STALE
```

### v10（target）

```
agent → graph_merge_object(impl_content="function X(){...}")
         → graph 内存表
         → 持久化到 K/graph.json
         → typecalc_compile（读 graph.Objects[X].ImplContent）→ bundle.ContentHash
         → session_build（graph → index.html，纯投影）
         → review（比对 bundle.ContentHash vs hash(current ImplContent)）→ ALWAYS FRESH（同内容）
                                                                          → 不存在 cascade
```
