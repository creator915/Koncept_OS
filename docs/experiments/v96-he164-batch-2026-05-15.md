# HumanEval 全量 Batch — kcpos v9.6 — 2026-05-15

OpenAI HumanEval 全部 164 题，由 kcpos 端到端跑一遍。报告聚焦**任务完成情况**与**流程合规度**，并给出两个口径的得分对比。

> HumanEval（OpenAI 2021，Codex 论文随附）：164 个单函数 Python 任务，每题给函数签名 + docstring，要求生成可通过隐藏 `check(candidate)` 测试的实现。公开 leaderboard 上 frontier model 单次 pass@1 通常 67–92%。

## 1. 任务范围

- 全部 164 题（HumanEval/0 – HumanEval/163）
- fixture 自动从 OpenAI 原始 `HumanEval.jsonl` 生成 `SPEC.md`（5 个早期手写 fixture he0/14/22/23/24 保留原状）
- 输入：每题一份 `SPEC.md`（目标 + 函数签名 + 行为契约 + docstring 示例）
- 输出要求：单文件 `code.py`，顶层导出 entry_point 函数
- 模型：`deepseek-v4-pro`
- 并发：10（自写 controller `run_he_batch.py`，带 resume + 状态板）
- 时长：约 6 小时（10:25 → 16:25）

## 2. 总体结论

| 口径 | 分数 | 含义 |
|---|---|---|
| **kcpos 自评 PASS** | **162 / 164（98.8%）** | chain 走完 + checkpoint `finalVerdict=PASS` |
| **HE 官方 pass@1** | **159 / 164（97.0%）** | OpenAI 原始 `check(candidate)` 跑生成代码 |

两个口径只差 ~3 题——说明 kcpos 的自评与真实正确性**高度吻合**，不是「自评虚高」。97.0% 显著高于裸模型单次 pass@1 的常见区间。

## 4. 流程合规度

- **chain 全链路稳定性**：162/164 完整跑通 compile → describe → synthesize_tests → test → review → finalize，PASS 率 100%（在完成的 162 题里）
- **自评 vs 真值吻合度**：自评 PASS 162 题中，159 题官方也 PASS；仅 3 题（he148/155/159 类）自评通过但官方挂——合成的测试 case 没覆盖到 tuple/list 返回类型差异
- **v9.6 加固保持**：全程未观察到 fake-PASS、未观察到主对话越权写 impl、未观察到 evidence 篡改；2 个新 chain 漏点（见 §6）属新发现，非已修项回归
- **自我纠错可观察**：he89、he92 第一次 finalize 时 verdict=FAIL，agent 未退出、继续修复后第二次 finalize 改 PASS——chain 内的 retry 机制有效（早期监控误把中间 FAIL 态当结果，已在方法学 §7 修正）

## 5. 失败分类与 root cause（5 题）

| 题 | 现象 | root cause | 归属 |
|---|---|---|---|
| he148 (bf) | 返回 `[]` list，官方期望 tuple `()` | LLM 把 tuple 实现成 list | kcpos：tuple/list 类型混淆 |
| he155 (even_odd_count) | 返回 `[evens,odds]` list，期望 tuple | 同上；且收尾阶段 agent 反复重试把原本 PASS 的 code.py 改坏 | kcpos：类型混淆 + 自我改坏 |
| he159 (eat) | 返回 `{dict}`，官方期望 `[total,left]` array | spec 理解偏差 | kcpos：spec 理解 |
| he20 (find_closest_elements) | 重复元素时配对顺序不符 | 算法 edge case | kcpos：算法 |
| he38 (decode_cyclic) | code.py 只定义 decode_cyclic，官方 check 需配对的 encode_cyclic 做 round-trip | fixture 生成脚本只提取 entry_point 的 docstring，未告知 agent 还需实现配对的 encode 函数（对比 he50 decode_shift：agent 自行推断出需要 encode_shift，故 PASS） | **评测 harness 的 SPEC 生成缺陷**，非 kcpos 实现错 |

**纯 kcpos 实现失分仅 4 题**（he20/148/155/159），核心失分点是 HumanEval 经典的 **tuple-vs-list/dict 返回类型坑**（docstring 说 "return a tuple/array"，LLM 习惯返回 list/dict）。he38 是评测侧 SPEC 生成对「成对函数题」处理不足，不计入 kcpos 能力评估时，可比口径 ≈ **159/164 ≈ 97%**。

## 6. 新发现的 chain 漏点（2 个，v9.6 范围外）

| # | 题 | 现象 | 待修方向 |
|---|---|---|---|
| 6.1 | he59 | `typecalc_test` 调 subprocess 跑 pytest 无 timeout 保护；LLM 合成的 test case 含慢算法（LargestPrimeFactor 大整数分解）→ subprocess hang 1h48min 未返回，占用并发 slot | `runPythonTest` 的 subprocess 加超时（30–60s）+ 超时归类为 TestError 而非 hang |
| 6.2 | he138 | LLM stream 在 emit 过 partial content 后中断，kcpos 客户端不重试直接退出（与 ProgramBench fx 第 1 轮死法同源） | transcript-level auto-resume，或 emit 前 buffer 整段 message 使重试安全 |

二者均靠 controller 的 `dead-without-checkpoint` 检测兜底（自动补位、不卡 batch），但单题进度丢失。164 题中各触发 1 次，发生率 1.2%。

## 7. 评测方法学（透明记录）

初版 scorer 把交付物当独立 module import、官方 `check()` 在隔离命名空间 exec——两者不通，导致 he32/he33/he38/he50 的 check 引用同模块辅助函数（`poly`/`sort_third`/`encode_cyclic`/`encode_shift`）时 NameError，被误判 ERROR。该口径下报 156/164=95.1%，**偏低**。

修正：scorer 改为在交付物模块的命名空间内 exec `check()`（与 OpenAI 参考 harness 一致——prompt+completion+test 在同一 globals）。修正后 he32/he33/he50 回归 PASS，得到准确口径 **159/164 = 97.0%**。he38 修正后仍 ERROR——确认是真问题（§5）。

监控侧另一处方法学修正：早期在 agent 仍 running 时读 checkpoint，命中过 finalize 中间态（FAIL），误判为最终结果。已改为仅在进程退出后判定。
