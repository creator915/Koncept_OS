## 诚实结论(重点,别被 4/4 误导)

1. **本批没有验证门禁的"抓"能力——那恰恰是设计的核心、也是难的一半。** 4 个跑通的任务里,DeepSeek **把维护任务全做对了,且一个怪癖都没改坏**(隐藏 preserve+accept 全过)。于是只观察到 true-allow,**0 个 true-catch**。"LLM 真把 load-bearing 怪癖改坏时,kcpos 锁复检能不能抓住"——这个端到端**没被这批触发过**。它目前只有单测证据(`TestGate_MethodUseRule_FiresOnArtifactDrift`、非确定性守卫测试),没有活体 LLM 回归证据。

2. **本批真正验证了的是"容易的一半"**:跨 4 个不同怪癖函数,恢复出的 characterization 锁**没有过度约束**——0 false-alarm,且与独立隐藏 oracle **4/4 一致**。即:锁是忠实、不噪的代理,端到端闭环能跑通。这是真结果,但不是设计的卖点(卖点是"抓改坏")。

3. **为什么没破**:fixture 的 legacy 注释直白写了"不要 fix 这个怪癖" + TASK 写了"preserve existing behavior"——等于把怪癖**剧透**给了模型,DeepSeek 老实保留了。这是 **fixture 设计缺陷**:我想要的对抗样本没出现。

4. **pb-range 是真失败**:characterize 第一步 synthesizer 返回无结构化用例(`synthesizer produced no structured cases`),0 锁,闭环根本没起步。具体 gap:synth 罢工 → 无锁 → 棕地闭环不能启动。属 ITERATION 级问题。

## 不报的东西

- 不报 PB 分数(非 benchmark,且 5 题里 1 题 harness 挂)。
- 不声称"门禁有效"——本批只证明了不误报,没证明能抓。

## 要补什么才算真验证了核心论点

1. **forced-break 对照**:harness 注入一个**已知会改坏怪癖**的修改(不靠 LLM 偶然犯错),端到端看锁复检是否 `true-catch`。这才直接打门禁的"抓"路径。
2. **去剧透 fixture**:legacy 注释别明写怪癖,TASK 别明写 preserve——逼近真实棕地(代码即唯一规格)。
3. **修 pb-range**:synth 罢工时的回退(raw testCode 模式 / 重试 / 换 probe 策略)。
